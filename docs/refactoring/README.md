## 段階と完了条件

順序はR1→R2→R3→R4→R5を基本とする。R3の比較用データは、各段階で既存の性能テストを実行した際にも保存する。各段階の大きさは異なるため、完了数を全体の進捗率には換算しない。

| ID | 段階 | 状態 | 成果と完了条件 |
| --- | --- | --- | --- |
| R1 | 拘束生成をSelectionから分離 | 完了 | 対象を明示的に渡して判定・生成できる。生成のための一時的なSelection書換えを除去し、事前選択・逐次選択・途中取消の既存挙動を維持する |
| R2 | 編集の確定・取消・履歴を整理 | 未着手 | 開始・preview・確定・復元の責務を分離。共通部分と操作固有部分を区別し、TX-01〜05とDocument／Block Editorの履歴を維持する |
| R3 | ドラッグの処理別測定と改善 | 未着手 | solve・依存更新・描画・UI更新の時間と実行回数を同条件で比較できる。測定で特定した箇所を改善し、拘束精度・固定対象・追従量を維持する。改善対象が特定できなければ測定結果と残課題を明示する |
| R4 | 責務ごとのモジュール分離 | 未着手 | R1〜R3で境界が明確になった処理から移動。入出力・依存方向を説明でき、分離対象の旧経路と重複処理を除去する。file起動・HTTP起動、保存形式・GeometryRefを維持する |

R4でapp.js全体を一度に分割しない。具体的な抽出対象は先行段階の結果から決め、この表を更新する。R5ではテスト件数の減少自体を目標にしない。

## 各作業の進め方

1. 対象IDを「作業中」にし、関連仕様・実装・テストを確認する。
2. 1つの責務を小さな差分で変更する。新しい挙動や復元範囲の判断が必要になった場合は、選択肢と影響を示してユーザーへ確認する。確認が必要な部分だけを「確認待ち」にする。
3. 関連する既存テストを必ず実行する。状態を変える経路では成功・失敗・取消後のDocument、参照、Undo／Redoを確認する。計算やドラッグに影響する変更では、同じfixture・環境で精度と性能も比較する。
4. specとの一致、不要な旧経路、デバッグ出力、関係のない差分を確認してCommit・Pushする。進捗表と現在地を同じ作業の中で更新する。
5. 段階の終了時に全体検証を行い、結果とcommitを記録する。developへ統合後、統合済みの作業ブランチを削除し、次段階は新しいブランチで開始する。

「完了」は成果物・必要な検証・Commit・Pushが揃った状態とする。段階の完了にはdevelopへの統合も含む。検証未実施・失敗・確認待ちを完了へ含めない。予定を変更するときは対象と理由を更新し、日々の詳細ログを別文書に増やさない。

| 対象 | 結果 | 根拠・制限 |

| R2〜R5 | 未実施 | 各段階の完了時にコマンド、結果、対象commit、比較条件を追記する |

R1の測定条件はWindows x64、Node v24.11.1、Playwright Chromium revision 1223、1 worker、既存fixtureと既存閾値。全複雑度fixtureの拘束入力48操作は最大94ms（commandの上限250ms／対象clickの上限350ms）、最大solve 3ms。ドラッグsuiteも既存の精度・追従・時間条件を通過した。これは同環境での回帰確認であり、実図面の遅延解消や有意な高速化を示す比較ではない。

通常の成功、expected failure、skip、予期しない失敗を区別する。性能値はfixture、browser、環境、測定条件と一緒に扱い、合格させるために閾値を緩めない。
