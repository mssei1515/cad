# 仕様整理と段階的リファクタリング

ここは仕様整理・移行・実装分離の開発資料。現在の正式仕様は[spec/README.md](../../spec/README.md)を参照する。未採用の草案を実装の根拠として使用しない。

## 目次案の位置づけ

「基本概念／共通契約／機能別操作／UI／データと互換性／計算契約／検証対応」の7領域を、仕様整理の到達先として採用する。各領域を複数の文書に分けた**移行先のファイル構成、現状との対応、作業順序**を[仕様の移行計画](./migration-plan.md)にまとめた。

これは文書構成の計画であり、製品の挙動や内部モデルを新たに決定するものではない。正式仕様の再配置はM1から着手し、領域ごとに進めている。

## 現在地と次の作業

現在は仕様整理の途中。編集の確定と失敗（TX）、削除と参照（DEL）、外観（APP）、読込（LOAD）の規則を既存構成の中で集約し、関連テストを補強した。UI、計算契約、機能固有の操作には未整理の記述が残る。

M1で基本概念と入口を移行し、実装配置・改善予定を開発資料へ移した。M2では所属・編集可否・履歴と採用済み共通契約を集約し、削除の操作手順を分離した。本番コードの分割と性能比較は未実施。内容の「採用済み」と、文書の「移動済み」を分けて管理する。

次の作業は移行計画の**M3：保存形式・読込互換性・ファイル操作の分離**。以後は操作・UI、計算契約の順に進め、各工程で検証対応を更新する。

## 記述の形

機能ごとに必要な項目だけを記載する。空欄を埋めるために仕様を増やさない。

1. 対象と前提条件
2. 入力・操作
3. 成功時の結果
4. 取消・失敗時の結果と復元範囲
5. 履歴・永続化
6. 共通契約への参照と固有の例外
7. 対応する検証

共通ルールの本文は一か所へ置く。概要からはリンクし、数値や条件を再掲しない。ルールには変更後も追跡できるIDを付け、テストはIDと保証内容を対応させる。草案のIDは正式仕様へ採用した時点で固定する。

## 実装分離との関係

対象領域の仕様・回帰テスト・現状の性能を揃えてから、操作の確定／復元、計算実行、依存更新などの責任を段階的に分離する。全仕様の完成を待って一括で書き直さない。

E2Eの削減と実装の大幅変更は同時に行わず、移した保証が新しいテストで成立してから旧テストを除く。文書の再配置だけで拘束エラーやドラッグ遅延が解消したとは扱わない。
