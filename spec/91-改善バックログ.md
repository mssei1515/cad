# 改善バックログ

この文書は仕様ではなく、コード調査から得た改善候補である。優先度は、今後 Presentation を安全に拡張するための順序を重視している。

## 1. 要約

最大の課題は、`app.js` 16,058行に Document 状態、ドメイン処理、Canvas 描画、DOM、入力状態機械、保存、Block Editor、Presentation、テスト fixture が同居していることである。

単なるファイル分割だけでは循環依存を移すだけになる。先に次の境界を定義する必要がある。

```text
Domain model
  Geometry / Constraint / Sketch / Block / Presentation

Application services
  Command / History / Solve orchestration / Reference lifecycle

Infrastructure
  Serialization / Migration / Download / Import

Adapters
  Canvas renderer / Hit testing / DOM UI / Test support
```

## 2. P0 — Presentation 拡張前に行う構造改善

### R-001: `app.js` の責務分割

根拠: `app.js` はトップレベル関数736、可変宣言74を持ち、描画と model mutation が相互に直接呼び合う。

問題:

- 変更影響範囲が読みにくい。
- 純粋関数と副作用が区別できない。
- Geometry と Presentation の名前上の分離に対し、実装境界がない。
- テストが巨大な closure 内部へ依存する。

方向:

1. まず副作用のない math、ID、target、serialization helper を ES module へ抽出する。
2. 次に Sketch、Block、Presentation の service を model 引数で呼ぶ形へ変える。
3. 最後に DOM event と Canvas renderer を adapter として分ける。

大規模な一括 rewrite は避け、同じ E2E を通しながら1境界ずつ移す。

### R-002: 編集スコープの抽象化

根拠: Block Editor は [`openBlockDefinitionEditor`](../app.js#L2704) で `model.points`、`model.lines`、`model.constraints`、`model.sketches` 等をドラフト配列へ差し替え、完了・キャンセルで戻す。

問題:

- 通常 Document と Block Definition のどちらを編集しているかが暗黙のグローバル状態になる。
- save、history、Presentation 禁止、入れ子 Editor rollback が条件分岐だらけになる。
- 将来の複数ビューや Presentation Editor と両立しにくい。

方向:

```text
EditingScope
  kind: document | block-definition
  geometryStore
  sketchStore
  constraintStore
  blockInstanceStore
  history
```

作図・拘束・solve は `EditingScope` を明示的に受け取る。Block Editor は model 全体の差し替えではなく、active scope の切替にする。

### R-003: コマンド状態機械の明示化

根拠: `mode`、`pendingCommand.type`、`pendingConstraintCommand`、多数の `*StartPoint` と `*DragSession` を、巨大な pointerdown/pointermove/keydown handler が組み合わせている。

問題:

- 状態組み合わせの不正値を型で防げない。
- Esc、mode 切替、Sketch 切替の cleanup が重複する。
- 新しい Presentation Tool を追加するほど分岐順序依存が増える。

方向:

```text
InteractionState
  Idle
  Selecting
  DrawingLine { start, rollback }
  PlacingDimension { target, phase }
  PlacingLeader { target, phase }
  Dragging { kind, session }
  EditingBlock { childState }
```

各状態へ `pointerDown`、`pointerMove`、`pointerUp`、`keyDown`、`cancel` を定義し、遷移時 cleanup を1箇所に置く。

### R-004: version 別 schema と migration

根拠: [`loadModelData`](../app.js#L3986) は408行あり、現行 loader 内で旧データ補正、Block graph 検証、オブジェクト生成、Presentation 正規化を一度に行う。`version` を保存するが分岐に使わない。

問題:

- どの旧形式まで互換か説明できない。
- 不正 JSON と旧 JSON の区別が曖昧。
- Presentation schema を変更すると loader がさらに巨大化する。

方向:

1. JSON Schema 相当の `DocumentV8Data` validator を作る。
2. `migrateVnToVnPlus1` の直列 migration にする。
3. validation、migration、runtime object hydration を分ける。
4. 代表的な旧 fixture の round-trip を固定する。

### R-005: 参照インデックスと削除ポリシーの共通化

根拠: `for (const sheet of model.presentationSheets)` による style・Annotation cleanup が Block 完了、Geometry 削除、Sketch 削除など複数箇所に重複する。Constraint 参照検索も毎回 graph node を走査する。

問題:

- 削除経路ごとに「拒否」「自動解除」「自動削除」が異なる。
- 新しい Presentation Element 型を追加すると全削除経路の更新が必要になる。
- 参照切れを黙って消すか保持するかがサービスではなく個別処理に埋まる。

方向:

```text
ReferenceIndex
  GeometryRef -> Constraint[]
  GeometryRef -> PresentationElement[]
  GeometryRef -> StyleOverride[]

applyGeometryChange(changeSet, policy)
  reject | remove-dependent | orphan-dependent
```

全削除・無効化・Definition 更新を `ChangeSet` と共通ポリシーへ集約する。

## 3. P1 — 重複を共通化する改善

### R-006: GeometryRef を値オブジェクト化

現状は裸の ID、`kind:id`、`instance@element`、`instance@nestedInstance@element` が場所ごとに文字列処理される。

方向:

- `GeometryRef { kind, path[] }` を定義する。
- parse、serialize、resolve、equality、ancestor Instance 抽出を1箇所にする。
- Constraint、Presentation target、style key で同じ resolver を使う。

効果: Block 入れ子、ID migration、参照切れ診断を安定化できる。

### R-007: DimensionTarget の共通化

根拠: Geometry 寸法と Presentation 注記寸法は、対象選択、値計算、保存、復元、配置、描画の大半を共有する一方、`distanceTarget...` と `presentationTarget...` に分かれている。

問題例: Presentation の Point–Point 軸が配置結果へ保存されず、表示値と寸法線方向がずれる可能性がある。

方向:

```text
DimensionTarget
  type: aligned | horizontal | vertical | point-line | line-line |
        line-length | angle | radius | diameter
  refs[]

MeasurementService.measure(target)
DimensionLayout.layout(target, placement)
```

「拘束として値を駆動するか」「実測を表示するか」だけを別ポリシーにする。

### R-008: Constraint serializer registry

根拠: [`serializeConstraint`](../app.js#L3456) と [`deserializeConstraint`](../app.js#L3867) が長い `instanceof` / `type` 連鎖で対になり、Constraint 追加のたびに複数箇所を更新する。

方向:

```text
constraintCodecs = {
  distance: { class, serialize, deserialize, refs },
  parallel: { ... }
}
```

同じ registry から参照列挙、保存、復元、表示名を提供する。未登録型を Block 化や保存前に一貫して検出する。

### R-009: 選択集合の抽象化

根拠: `selectedPoints`、`selectedLines`、`selectedCircles`、`selectedArcs`、`selectedBlockInstances`、Arc 端、Constraint、Dimension が別変数で、clear・toggle・copy・style 対象変換が重複する。

方向:

- discriminated union の `SelectionItem` と `SelectionSet` を導入する。
- Geometry Mode / Presentation Mode ごとに選択可能 policy を渡す。
- sidebar、Canvas、Constraint operand、Presentation target への変換を selector とする。

### R-010: Geometry renderer の共通化

根拠: `drawLines`、`drawCircles`、`drawArcs` は selection、hover、sidebar highlight、constraint status、construction、Presentation style の優先順位をそれぞれ重複実装する。

方向:

```text
RenderStyle resolveGeometryRenderStyle(item, context)
drawPrimitiveGeometry(item, style)
```

モード別 style policy と形状 path 描画を分ける。Point だけ Presentation style が不完全な問題も同じ policy で解消する。

### R-011: Block graph と Projection service の統合

根拠:

- 通常 runtime と loader 内に `DefinitionHasGeometry`、`GeometrySketchIds` の類似実装がある。
- Definition clone、merge、history serialize、Document serialize で同じ Geometry 構造を繰り返す。
- Projection 取得のたびに `ensureBlockState` が normalization を行い得る。

方向:

- `BlockGraph` に ownership、cycle、scope、usage を集約する。
- `ProjectionService` を pure input/output にする。
- Definition/Scope の共通 `GeometryStore` codec を使う。
- normalization は load と明示 command 境界だけで実行し、draw/hit test から mutation を排除する。

### R-012: 数学ユーティリティの重複除去

`normalizeAngle` と `arcEndpointPoint` は `app.js` と `constraint_solver.js` の両方にある。Line/Arc の方向、角度、投影、距離も類似 helper が増えている。

方向: Geometry kernel の pure utility module を1つにし、solver、dimension、trim、hit test、Presentation が参照する。

## 4. P1 — Presentation の具体的不整合

| ID | 問題 | 根拠 | 推奨 |
| --- | --- | --- | --- |
| P-001 | `visibleGeometrySketchIds` が保存されるだけで描画に未使用 | [`app.js`](../app.js#L327), 使用は正規化・削除だけ | Sheet 可視性モデルを決定し、実装するか field を削除する |
| P-002 | Annotation を選択・削除・style 編集できない | ヒット後は直ちに drag、Delete は Geometry Mode 限定 | 共通 Annotation selection と property editor を作る |
| P-003 | Point style の表示・非表示が効かない | [`drawPresentationPointHandles`](../app.js#L8492), [`hitPresentationElement`](../app.js#L12053) | Point を出力対象にするかを決め、render/hit policy を一致させる |
| P-004 | Point–Point 軸寸法が安定保存されない | [`presentationTargetToData`](../app.js#L10734) は target の既存 axis だけ保存 | 共通 DimensionTarget に horizontal/vertical/aligned を明示する |
| P-005 | Annotation Dimension の `style` が描画されない | `drawPresentationElements` から固定 style の `drawDimension` を呼ぶ | Annotation style token を layout/render へ渡す |

| P-008 | Presentation の E2E が少ない | 直接的な注記テストは主に drag 1件 | Sheet/style/全注記対象/save/delete/orphan の fixture を追加する |

## 5. P2 — テスト・性能・保守性

### R-013: テストフックを本体から分離

`installTestHooks` 以下約1,915行を `test-support/cad-test-hooks.js` へ移す。公開 API は UI command/service を呼び、内部変数を直接操作する fixture は必要最小限にする。

テストは次の3層に分ける。

1. Geometry kernel と codec の unit test
2. Application command と history の state test
3. Playwright の実UI E2E

### R-014: 派生 Geometry のインデックス

`allGeometryPoints/Lines/Circles/Arcs` はそれぞれ全 Block Projection bundle を組み立て、target 復元や hit test で反復検索する。

方向:

- revision ごとに `GeometryIndex` を構築する。
- `id -> item`、`kind -> items`、`sketchId -> items`、空間 index を持つ。
- draw、hit、Constraint hydration、Presentation ref resolve で共有する。

### R-015: DOM 更新差分化

`updateUI` は多数の一覧を `innerHTML` で再生成し、そのたびに listener を再登録する。大きなモデルで authoring 性能を圧迫しやすい。

方向: selector で変更領域を特定し、Sketch、Block、sidebar、toolbar を独立 update する。DOM row は ID keyed 差分更新する。

### R-016: 表示文字列と内部語彙の統一

UI は英語 `Geometry Mode / Presentation Mode` と日本語 Hint が混在し、コードにも英語エラーが残る。内部 ID、仕様用語、UI ラベルを辞書へ分ける。

## 7. 実施順序

### Phase 0: 特性テスト（2026-08-12 実施済み）

- 現在弱い Presentation の round-trip と参照削除テストを追加する。
- 保存 fixture を現行 v8 の golden data として固定する。
- リファクタリング前後の authoring/drag 性能値を記録する。

追加済みの安全網:

- 全永続Constraint型を含むv8意味的round-trip、代表v1互換、ID予約
- 参照削除、履歴transaction、Block Editor scope、Presentation非干渉、Adapter非破壊性
- Node unit test、全page runtime error監視、Canvas visual baseline 4件
- Playwright 103 testsとunit 3 testsを基準とする

特性テストで判明した既存ギャップは [実装対応表とテスト](./90-実装対応表とテスト.md) に記録し、Phase 0では製品挙動を変更していない。

### Phase 1: Pure core

- Math utility、GeometryRef、DimensionTarget、Constraint codec を抽出する。
- runtime 動作は変えない。

### Phase 2: Lifecycle と serialization

- ReferenceIndex、ChangeSet、version migration を導入する。
- 削除・無効化・Definition 更新の分岐を共通化する。

### Phase 3: EditingScope と command

- Block Editor の model 配列差し替えを廃止する。
- interaction state machine を段階的に導入する。

### Phase 4: Renderer と UI

- Geometry render policy、hit test、sidebar 更新を分離する。
- Presentation property editor と Sheet UI を作る。

### Phase 5: Presentation V1

- [Presentation](./06-Presentation.md) の D1〜D8 を決定済みにする。
- V1 完了条件を command、保存、UI、E2E で実装する。

## 8. 完了判定

リファクタリングはファイルが小さくなっただけでは完了としない。次を満たすことを判定基準にする。

1. Domain service が DOM、Canvas、Prompt に依存しない。
2. draw と hit test が model を正規化・変更しない。
3. Geometry 参照の parse/resolve/delete が1つの API を使う。
4. 通常 Document と Block Definition が同じ `EditingScope` 契約を使う。
5. Constraint 型追加で codec registry 以外の長い分岐を編集しない。
6. Geometry 寸法と Annotation Dimension が同じ測定・配置契約を使う。
7. Playwright に加え、pure module の高速 unit test がある。
8. 全E2Eと性能基準がリファクタリング前後で悪化しない。
