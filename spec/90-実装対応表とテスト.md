## 3. 自動テストの守備範囲

### 強い領域

- 複雑な完全拘束 fixture と自由度解析
- 拘束付き Point、Line、Circle、Arc、Arc 端点のドラッグ
- 作図・拘束追加の性能上限
- 対称、接線、角度、寸法表示、トリム、オフセット
- Sketch 表示、削除、先祖参照、循環・範囲外参照
- Block 作成、配置、回転、構成、保存、入れ子、Editor 履歴、ロールバック
- コピー、切り取り、貼り付け、Undo/Redo

### 弱い領域

- Presentation Sheet の追加、名前変更、切替、保存を一連のUI操作で確認するテスト
- Geometry style の全プロパティ、複数選択、Sheet 間分離、Block Projection への適用
- 注記寸法の全対象組み合わせを UI から作成・保存・再読込するテスト
- 水平／垂直 Point 寸法の Presentation 保存
- Leader の作成、キャンセル、Geometry 追従、再読込
- Presentation Element の削除・style 編集。機能自体が未実装
- Geometry 削除時の参照切れ Presentation UX
- `visibleGeometrySketchIds`。機能自体が描画へ未接続
- JSON schema 境界値、ID 重複、未知 version の明示的テスト

`presentation-annotations.spec.js` という名前のファイルは Geometry・Sketch・UI の回帰テストも多数含み、Presentation 専用テスト群にはなっていない。

## 4. テストフック

`app.js` の [`installTestHooks`](../app.js#L14144) から末尾まで約1,915行あり、`window.__cadTest` に大量の fixture 作成・内部操作を公開する。`?test=1` のときだけインストールするが、コード自体は本番スクリプトに同梱される。

この方式は細かい内部検証に役立っている一方、次の問題がある。

- 本体ファイルの責務と行数を増やす。
- テストが内部関数・可変状態へ強く結合する。
- 実UI経路を通らない回帰テストが増えやすい。
- 本番とテスト支援コードの境界が見えにくい。

改善案は [改善バックログ](./91-改善バックログ.md) に記載する。

## 5. 検証コマンド

```powershell
npm run check
npm run test:e2e
```

`npm run check` は JavaScript の構文検証であり、lint、型検査、Markdown link、JSON schema は検証しない。

`npm run test:e2e` は Playwright 全件を実行する。一部性能・ドラッグテストは複数ケースを1つの `test()` 内で回すため、表示件数より実行ケースが多い。

## 6. 仕様更新時の確認項目

1. 実装済みと設計案を同じ断定表現で混ぜていないか。
2. 保存形式の変更は `version`、migration、round-trip テストを伴うか。
3. 新しい Geometry 参照は通常 Geometry、Block Projection、入れ子 Projection で同じように解決できるか。
4. Geometry 削除、Sketch 削除、Block 編集、構成無効化の全経路で参照ライフサイクルが一致するか。
5. 通常 Document と Block Editor の両スコープで動くか。
6. Undo/Redo、保存・読込、キャンセルの各境界をテストしたか。
7. Presentation の変更が solve 変数や Constraint を変更していないか。
